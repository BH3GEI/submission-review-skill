# 判定标准（默认口径）

比赛有自己的规则或组织方定了口径时，以那个为准；这里没有覆盖的情形，按总原则推。

## 总原则

只认定有直接证据的违规。核心问题有两个：

1. **产出是不是智能体在这次运行里当场做出来的？** 平台给的起点不算在内。
2. **它有没有用到规则不允许的信息？** 例如未公开的测试，或者通过不该有的渠道拿到的答案。

由此推出：

- 针对题目准备的提示词、经验、验收规则说明、空壳模板、通用模块，统称"预置知识"，属于正常优化，不判违规。
- 把赛前写好的产出原样交上去，也就是"硬编码答案"，判违规。这类证据可以直接拿文件比对，最扎实。
- 不抓预置知识，因为这类证据不够硬，容易引起争执。

自动审查工具常用一票否决：只要有一条错误，就整体判作弊。复核时要逐条分清轻重，不能沿用它的总结论。

## 情形与结论

| 情形 | 结论 | 怎么确认 |
| --- | --- | --- |
| 智能体识别出题目，把赛前写好的整套产出放进输出 | 不予通过 | 产出与预置文件逐字节相同，或扣除公共代码和起点后有效行重合 99% 以上；能找到"识别题目 → 复制"的代码路径；这一阶段模型调用极少，甚至为零 |
| 平台给了起点（如继承的上一轮产出），智能体把起点挪走，换成包里带的、已经做完本轮要求的版本 | 不予通过 | 产出与包内版本一致；能找到挪走或覆盖起点的代码；版本历史和运行记录里没有本轮的模型修改 |
| 模型写了代码，但程序用预置成品把它整个替换掉 | 不予通过 | 运行记录里模型写的文件没有进入最终产出；最终产出与成品一致 |
| 同一道题的多个阶段交的是同一份产出，后面的阶段没有重新生成 | 不予通过（与上面几条同时出现时作为佐证） | `app` 子命令里"各份产出之间相同文件的比例"；前面的阶段就带着后面才要求的功能 |
| 带着与隐藏测试高度相同的测试，并用来对答案、驱动修改 | 待定，倾向不予通过 | `tests` 子命令；先查清测试来源：是否曾公开、是否经平台泄露、是否只是照题面写的 |
| 篡改或伪造费用、用量记录 | 不予通过 | 对照平台后台的用量记录 |
| 实际调用了比赛指定以外的模型 | 不予通过 | 看请求最终发往哪里 |
| 智能体代码里有读取隐藏测试的设计，但运行时测试还不存在 | 通过（附注） | 向组织方确认测试出现的时机；运行记录里目录为空，或没有读到内容 |
| 模型自己产生了找测试的念头，但什么也没拿到 | 通过（附注） | 运行记录里返回为空；选手代码和提示词里没有让模型去读测试的指令 |
| 产出在被测试时记录测试发来的请求，随产出带回给选手 | 通过（附注），除非规则禁止 | 记录的写入代码、分界标记，以及带回文件里测试期间的内容；智能体在运行中是否读取并利用了这些记录 |
| 从平台返回给选手的反馈（测试报告、日志）里总结出验收规则或具体数据值，写进提示词或自检 | 通过（附注），写明内容、来源和可能影响的测试数 | 包里出现了题面没写、只在反馈里出现过的值；查清它来自平台正常返回的材料。是否允许属于规则问题，由组织方决定 |
| 为花满预算发送无意义请求 | 不单独作为不予通过的理由 | 这是真实花费，不是伪造账单；可以作为加重情节写进记录 |
| 针对题目的提示词、经验、验收规则说明 | 通过 | 内容里没有产物代码，只是把公开题面换个说法 |
| 空壳模板、通用模块、与题目相关的计算核心（不含页面、接口和数据） | 通过；与题目相关时附注 | 扣除起点后重合低，重合部分是脚手架或底层模块，页面、接口、数据都由模型完成 |
| 用 `npm install` 等方式安装依赖 | 通过 | 关键是查装了什么，而不是有没有装。都是公开通用包就不算问题；如果装的是选手自己发布的包，要看包里是不是答案 |
| 模型请求先发到本机，再转发到平台注入的地址 | 通过 | 跟踪转发目标，确认最终发往平台地址 |
| 代码里写了默认外部地址，但运行时会被平台注入的地址覆盖 | 通过 | 确认平台一定会注入该变量，默认值不会生效 |

## 重合比例怎么读

- **先扣基线。** 计算前必须扣掉官方模板、官方运行时、公开框架及其历史版本，以及平台给的起点。不扣的话，基于同一个公开框架的选手会被误判为高重合；继承了上一轮产出的选手，也会被算成"预置"。
- **逐字节相同，或 99% 以上：** 基本可以定性为复制，再找到复制的代码路径即可。
- **约 30% 以下，且重合的是配置、入口、存储和运行时代码：** 正常的模板复用。
- **中间区间：** 打开重合最多的文件逐个看，判断重合的是脚手架，还是业务功能（题面里的按钮名、报错文案、具体页面）。
- **比例不是作弊率。** 有继承起点时，要看版本历史里本轮改了多少、改的是不是本轮要求的内容。

## 代码同源（多账号）

**怎么判断是否同源：**

1. 智能体包内容完全相同（压缩包 sha256 一致，或解压后的文件全部一致）。
2. 扣掉公共代码后，有效行仍然高度重合。
3. 包内的版本号、版本说明文件是连号的，显示出自同一条开发线。
4. 用报名信息交叉核对，例如邮箱、学校、队伍名。这一步由组织方做。

代码同源只能说明出自同一个开发者。它可能是一人多号，也可能是组队后各自提交，或者代码被分发了。具体是哪种情况，要靠报名信息来区分，复核记录里不要替组织方下结论。

**怎么处理：**

- 默认每组只保留排名最高的一个账号，其余账号写"待定（代码同源）"，交组织方确认。
- 如果明显是一人多号来多拿评测次数，可以建议整组不予通过，由组织方拍板。例如大量账号用随手填的邮箱注册，跑的是同一套未公开的代码。
- 只是基于同一个公开框架修改的，不算同源证据。

## 换提交申诉

1. **技术核实。**
   - 选手发来的包，sha256 是否等于赛期内某次提交。
   - 那次运行的产出是否由模型生成：看运行时长、工具调用次数、用量，以及扣除基线后与预置文件的重合。
2. **规则判断交给组委会。** 比赛允许选手自己选定最终提交时，默认是"留哪份就评哪份"。如果给一个人改选的机会，同类情况的其他选手也应得到同样的机会。复核记录只写技术结论，并写明这条规则上的考虑。
