# 判定标准

## 总原则

只认定有直接证据的违规。核心问题只有一个：**交上去的应用，是不是模型在这次运行里当场写出来的。**

- 针对题目准备的提示词、经验、验收规则说明、空壳模板、通用模块（统称"预置知识"），都属于正常优化，不判违规。
- 把赛前写好的应用原样交上去（"硬编码答案"），判违规。这类证据可以拿文件直接比对，最扎实。
- 抓"预置知识"证据不够硬，容易引起争执，所以不抓。

自动审查（如 competition-anti-cheat）是一票否决：只要有一条错误就整体判作弊。复核时要逐条分轻重，不能沿用它的总结论。

## 情形与结论

| 情形 | 结论 | 怎么确认 |
| --- | --- | --- |
| 智能体按题目名识别题目，把预先写好的整套应用复制交上去 | 不予通过 | 交上去的应用与预置文件逐字节相同，或有效行重合 99% 以上；能找到"题目名匹配 → 复制"的代码路径 |
| 模型写了代码，但程序用预置成品把它整个替换掉 | 不予通过 | 运行记录里模型写的文件不在最终提交里；最终提交与成品一致 |
| 同一道题的多个阶段交的是同一份应用，后面的阶段没有重新生成 | 不予通过（与上两条同时出现时作为佐证） | `app` 子命令的"各应用之间相同文件的比例"；第 1 阶段就带着后面阶段才要求的功能 |
| 带着与隐藏测试高度相同的测试，并用它们对答案、驱动修改 | 待定，倾向不予通过 | `tests` 子命令；先查清测试来源（是否曾被公开、是否经平台泄露） |
| 篡改或伪造费用、用量记录 | 不予通过 | 对照平台后台的用量记录 |
| 实际调用了比赛指定以外的模型 | 不予通过 | 看请求最终发往哪里 |
| 智能体代码里有读取测试目录的设计，但运行时测试还不存在 | 通过（附注） | 向组织方确认测试复制进容器的时机；运行记录里目录为空 |
| 模型自己产生了找测试的念头，但什么也没拿到 | 通过（附注） | 运行记录里返回为空；选手代码和提示词里没有让模型去读测试的指令 |
| 为花满预算发送无意义请求 | 不单独作为不予通过的理由 | 这是真实花费，不是伪造账单；可作为加重情节写进记录 |
| 针对题目的提示词、经验、验收规则说明 | 通过 | 内容里没有应用代码，只是把公开题面换个说法 |
| 空壳模板、通用登录模块、自测小工具 | 通过 | 最终应用与预置文件的重合低（初赛中这类选手约 1%–28%），且重合部分是脚手架而不是业务代码 |
| 用 `npm install` 等安装依赖 | 通过 | 查装了什么，而不是有没有装。都是公开通用包就不算问题；如果装的是选手自己发布的包，要看包里是否就是答案 |
| 模型请求先发到本机、再转发到平台注入的地址 | 通过 | 跟踪转发目标，确认最终是平台地址 |
| 代码里写了默认外部地址，但运行时被平台注入的地址覆盖 | 通过 | 确认平台一定会注入该变量，默认值不会生效 |

## 重合比例怎么读

- **逐字节相同、或 99% 以上：** 基本可以直接定性为复制，再找到复制的代码路径即可。
- **约 30% 以下，且重合部分是配置、入口、数据库运行时：** 正常的模板复用。
- **中间区间：** 打开重合最多的文件逐个看，判断重合的是脚手架还是业务功能（题面里的按钮名、报错文案、具体页面）。
- 计算前必须扣掉公共代码（官方空白模板、官方 runtime、公开的开源框架及其历史版本）。不扣的话，基于同一个公开框架的选手会被误判为高重合。

## 代码同源（多账号）

**怎么判断是否同源：**

1. 智能体压缩包逐字节相同（sha256 一致）。
2. 扣掉公共代码后，有效行仍高度重合。
3. 包内的版本号、版本说明文件连号，显示是同一条开发线。
4. 用报名信息交叉核对（邮箱、队伍名等），这一步由组织方做。

代码同源只能说明出自同一开发者。它可能是一人多号，也可能是组队后各自提交，或者代码被分发。具体是哪种情况，要靠报名信息来区分，复核记录里不要替组织方下结论。

**怎么处理：**

- 默认每组只保留排名最高的一个账号，其余账号写"待定（代码同源）"，交组织方确认。
- 如果明显是一人多号来多拿评测次数（例如大量账号用随手填的邮箱注册、跑同一套未公开代码），可以建议整组不予通过，由组织方拍板。
- 只是基于同一个公开框架修改的，不算同源证据。

## 换提交申诉

1. 技术核实：选手发来的包的 sha256，是否等于赛期内某次提交；那次运行的应用是否由模型生成（看运行时长、工具调用次数、用量，以及与官方模板以外代码的重合）。
2. 规则判断交组委会：比赛允许选手自己选定最终提交时，默认是"留哪份就评哪份"。如果给一个人改选的机会，同类情况的其他选手也应得到同样的机会。复核记录只写技术结论，并写明这条规则上的考虑。
