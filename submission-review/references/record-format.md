# 记录格式与措辞

## 逐人记录 `<result_path>/<选手目录名>.md`

每人一份完整记录，结构固定。不要只给一句话结论。

```markdown
# <选手名>（<排名，如有>，<分数，如有>）

**结论：** 通过 / 通过（附注） / 不予通过 / 待定（<原因>）

## 概述
两三句话：应用是不是模型当场生成的，决定结论的那条证据是什么。

## 自动审查提出的问题及核实结果
### 1. <问题的白话描述>
- 核实结果：属实 / 部分属实 / 不属实
- 证据：`文件:行号`，必要的原文引用（英文原文后附中文意思）
- 是否构成违规：是 / 否，依据哪条标准
（逐条列出；没有自动审查结果时，写"未提供自动审查结果"，直接进入下一节）

## 提交的应用有多少来自事先准备的文件
按应用列出：文件数、逐字节相同的文件数、扣除公共代码后的重合比例，以及重合最多的几个文件和来源。

## 其他发现
自动审查没有提到、但复核中发现的问题；以及排除过的疑点（例如"已检查依赖清单，全部是公开通用包"）。

## 与其他账号的代码关系
（仅在有同源关系时写）属于第几组、依据是什么。

## 待确认
（仅在有时写）还缺什么信息、需要谁提供。
```

## 汇总表 `<result_path>/summary.csv`

UTF-8 带 BOM（Excel 直接打开不乱码），列为：

| 列 | 内容 |
| --- | --- |
| 选手 | 选手目录名或账号名 |
| 排名 | 如有 |
| 结论 | 通过 / 通过（附注） / 不予通过 / 待定（原因） |
| 理由 | 一段白话概述，一到两句 |
| 主要证据 | 最关键的一条，带 `文件:行号` 或重合比例 |
| 同源分组 | 如有，写组号 |
| 待确认 | 如有 |

批量模式下另写一份 `<result_path>/same-origin.md`：每组的成员、判断依据（逐字节相同 / 重合比例 / 版本连号），以及哪些相似来自公开框架、不能作为同源证据。

## 措辞

结论可能会被选手看到或引用，所以措辞要正式、留有余地，只陈述证据。

| 不用 | 改用 |
| --- | --- |
| 罪名 | 审查项、自动审查提出的问题 |
| 刷掉 / 放过 / 存疑 | 不予通过 / 通过 / 待定 |
| 多号、分身 | 疑似多账号、疑似同一主体 |
| 实锤、偷看、魔改、别杀太狠 | 证据确凿、读取隐藏测试、在某项目基础上修改、从宽审查 |
| 建议通过、建议不予通过 | 直接写结论 |
| 自动审查认为…… | 自动审查提出了……；复核结果是…… |

- 不写名词解释，不解释比赛怎么打分，看记录的人都清楚这些。
- 英文原文保留，后面附中文意思；路径、函数名、规则编号保持原样。
- 拿不准的写"待定"，并写清还差什么信息。
- 记录是给人工复核用的初稿：每份结论都要由人逐个确认后，才能对外发布。
