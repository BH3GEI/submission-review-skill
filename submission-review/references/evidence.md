# 证据从哪里找

最硬的证据是文件比对：产出和智能体里预置的文件是否相同。版本历史、运行记录和平台数据用来说明这次运行里模型实际做了多少事。

| 证据来源 | 看什么 | 典型信号 |
| --- | --- | --- |
| 智能体包 | 预置文件、写死的题目名、复制逻辑、读测试的代码、带回评测信息的代码 | 代码里写死题目全称；用 `copytree` / `copyfile` 把整个目录拷进输出；有存放成品的目录，例如 `snapshots/`、`applications/`、`official/`；注释或日志里写着 "no model calls" |
| 产出 | 与预置文件的重合 | 逐字节相同；同一道题的多个阶段交的是同一份；前面的阶段就带着后面才要求的功能 |
| 产出里的版本历史（如 `.git`） | 起点是什么、每次提交的时间、说明和改动行数 | 按需求逐项提交，且改动与需求对得上，说明模型在做事。只有起点一次提交、内容与包内成品一致，或者起点被整体替换，都是复制的迹象 |
| 运行记录（选手自带的，或平台导出的） | 模型的思考和工具调用 | 模型写的文件没有进入最终产出；模型去读测试目录，以及读到了什么；读取了带回的评测记录 |
| 平台元数据和后台（只读） | 最终选定的是哪次提交、包的 sha256、运行时长、工具调用次数、token 用量和成本 | 某个阶段没有任何模型调用；时长和调用次数远低于同题其他选手。成本低只是线索：也有干净的选手花得很少 |
| 平台返回给选手的反馈 | 测试报告、日志、已评测的产出 | 包里出现了题面没写、只在反馈里出现过的具体值；查清这个值是不是平台正常返回的 |
| 隐藏测试 | 与选手自带测试逐行比对 | 大部分测试文件有 80% 以上的行相同，辅助函数和结构也一致，并且这些测试被用来驱动修改 |
| 公开题面 | 判断一段内容是不是只复述题面 | 按钮名、报错文案、示例账号都能在题面里逐字找到，说明只是照题面写的 |

## 使用注意

- **先扣基线。** 官方模板、官方运行时、公开框架及其比赛截止前的历史版本，都放进 `--baseline`。平台给了起点时，用 `history --export-start` 导出起点，一并放进去。基于同一个公开框架的两位选手，不扣基线时看起来可能有八成重合，扣掉以后可能一行都不剩。
- **测试的时序要向组织方确认。** 隐藏测试可能在智能体退出之后才放进容器，这时智能体代码里"读测试目录"的设计不会生效。但平台随后会启动选手的产出来跑测试，产出这时可能读得到测试，或者记下测试发来的请求，再随产出带回给选手。看到选手持有与隐藏测试高度相同的测试时，要考虑这条来源。
- **分清反馈和泄题。** 平台主动返回给所有选手的材料（如测试报告）属于反馈，从中总结出来的东西按"预置知识"处理并写附注。只有通过不该有的渠道拿到的测试内容，才按泄题处理。
- **注释和文档不是证据。** 选手代码里"这里不读取测试""这只是通用模板"之类的说法，都要顺着代码确认。说法与代码不符时，作为加重情节写进记录。
- **先核对自动审查报告的对象。** 自动审查的报告可能写的是别人的代码，或者内容乱码、缺失。
- **压缩包损坏要写明。** 恢复出来的文件要注明来源；恢复不了的部分不作为违规证据，在"待确认"里写清缺什么。
